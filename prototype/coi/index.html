Cross-origin isolation on GitHub Pages

A prototype, not part of the site. It answers one question: can this host give a page SharedArrayBuffer, which is what an LLVM-backed in-browser Rust toolchain needs?

Why it matters. The Rust compiler the site ships uses the Cranelift backend and cannot build parse::<i64>(). The alternative with the LLVM backend, rubrc, needs threads — and threads need SharedArrayBuffer, which a browser only grants to a cross-origin isolated document.

A server grants that with two response headers. GitHub Pages sends neither and cannot be configured to. A service worker can stand in by re-issuing the page's own responses with the headers attached. This page registers one — scoped to this directory, so it cannot touch the rest of the site — and reports what the browser then believes.

And whether it actually works

Being told crossOriginIsolated is not the same as a worker and the page sharing memory. This allocates a SharedArrayBuffer, hands it to a worker, has the worker write to it with an atomic, and waits for the value to appear on this side.
